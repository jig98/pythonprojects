A small pipeline that processes, filters, and reports on employee data,
built using iterators, generators, closures, decorators, and context
managers.

## Answers to Conceptual Questions

### 1. Iterator — `iter(employees)` vs. `next(iterator)`

`iter(employees)` **creates** an iterator object from an iterable (like a
list). It calls the iterable's `__iter__()` method and hands back a fresh
iterator that keeps track of position, but on its own it doesn't produce
any values.

`next(iterator)` **advances** that iterator and returns the next single
value from it by calling `__next__()`. It's a repeated, stateful action —
each call moves the internal position forward by one, and it eventually
raises `StopIteration` once there's nothing left.

In short: `iter()` is the one-time setup step that gives you an iterator;
`next()` is the repeated step you use to actually pull values out of it.

### 2. Generator — Why prefer `yield` over returning a complete list?

With `yield`, a generator produces values **lazily**, one at a time, only
when they're asked for. This means:
- **Memory efficiency** — a huge dataset (e.g. millions of employee
  records) never has to exist in memory all at once; only the current
  item does.
- **Speed to first result** — the caller can start processing the first
  item immediately instead of waiting for the entire list to be built.
- **Composability** — generators can be chained (as in this project,
  `employee_generator` feeding into `filter_by_department`) so data
  flows through a pipeline without ever materializing intermediate
  full lists.

Returning a complete list forces Python to build and hold the entire
result in memory before you can use any of it, which doesn't scale well
for large datasets.

### 3. Generator vs Iterator — Is a generator an iterator?

Yes. Every generator **is** an iterator: it automatically implements both
`__iter__()` (which returns itself) and `__next__()` (which resumes the
function until the next `yield` or raises `StopIteration` when the
function ends). What makes generators special is that you don't have to
write a class with manual state tracking (like `EmployeeIterator` does)
— the `yield` keyword and Python's generator machinery handle the
iterator protocol for you automatically. So: all generators are
iterators, but not all iterators are generators (custom classes like
`EmployeeIterator` are iterators without being generators).

### 4. Closure — Why does `check()` still know `min_salary`?

```python
def create_salary_filter(min_salary):
    def check(employee):
        return employee["salary"] >= min_salary
    return check
```

When `check` is defined inside `create_salary_filter`, it references the
enclosing function's variable `min_salary`. Python detects this and
creates a **closure**: the inner function keeps a reference to the
variables it needs from the enclosing scope, bundled together with the
function itself. Even after `create_salary_filter()` finishes executing
and its normal local scope would otherwise be discarded, `min_salary`
stays alive because `check` still holds a reference to it. That's why
calling `high_salary(employee)` later still "remembers" the value of
`min_salary` that was passed in when the closure was created.

### 5. Decorator — What does `@log_execution` approximately mean?

```python
@log_execution
def generate_report():
    ...
```

is roughly equivalent to writing:

```python
def generate_report():
    ...

generate_report = log_execution(generate_report)
```

In other words, `@log_execution` takes the function defined right below
it, passes it into `log_execution` as an argument, and replaces the
original name (`generate_report`) with whatever `log_execution` returns
(here, the `wrapper` function). Every future call to `generate_report()`
now actually calls `wrapper()`, which runs the "before" logic
(`[START] ...`), calls the original function, then runs the "after"
logic (`[END] ...`) — all without changing a single line inside
`generate_report` itself.

### 6. Context Manager — Why is `with ReportFile(...)` better than manual open/close?

```python
with ReportFile("report.txt") as report:
    ...
```

is better than manually calling `open()` and `close()` because:
- **Guaranteed cleanup** — `__exit__()` runs even if an exception is
  raised inside the `with` block, so the file is always closed. A manual
  `file.close()` placed after some risky code can be skipped entirely if
  an error occurs first.
- **Less boilerplate** — no need for a `try/finally` block every time you
  want to safely handle a resource.
- **Clear scope** — the file is only "alive" and usable within the
  indented `with` block, which makes it obvious to a reader exactly
  where the resource is open and in use.
- **Reusability** — the open/close logic lives in one place
  (`ReportFile`), so every part of the program that needs to write a
  report reuses the same safe behavior instead of duplicating
  open/close code.
